## 1. 已确认的接入路径

安装包 `kernelmind-apex 1.0.7.7t` 的 `joint_cmd_mux` 支持：

| Input值 | 来源 |
|---|---|
| 0 | idle / None |
| 1 | Teleop，实际接QP输出 |
| 2 | Planner |
| 3 | user，自定义关节来源 |
| 4 | replay / Playback |

网页只显示0/1/2/4，但二进制启动日志与隔离服务测试均确认3存在。来源3读取相对命名空间中的 `control/user/joint_cmd_A/B`，类型为JointcmdArm；选择后转发到 `control/joint_cmd_A/B`。

候选路径因此可以调整为：

```text
ForceVLA TCP → 独立同核心QP → 会话/时效/约束保护层
    → /tj/control/user/joint_cmd_A/B → Input=3 → 现有mux → ROS驱动
```

这是接入候选，不是已部署配置。它不需要往遥操已经使用的 `/tj/control/ik_request` 增加发布者。原有“共享IK入口有发布者”的发现仍成立，但不再意味着所有可能的接入路径都被遥操占用。夹爪仍是独立控制通道。

本机找到安装二进制、头文件和QP静态库，尚未找到 `joint_cmd_mutx.cpp` / 机器人驱动的对应完整源码。此结论仅限已搜索的本机目录与安装包。

## 2. 实际二进制的隔离测试

[最终测试报告](../../data/integration-runs/20261014-mux-guard-live-ramp/report.json)使用已安装mux二进制的独立进程，固定ROS_DOMAIN_ID=231（在用机器人为24）、随机 `/forcevla_sandbox_*` 命名空间及本机通信范围。没有启动机器人驱动、没有连接SDK、没有调用 `/tj` 服务。

测试记录二进制SHA-256，最终采用与在用启动参数相同的3秒过渡设置。合成反馈/指令仅用于检验消息路由，不代表合理的真实机器人关节姿态；不能复制为实机动作。

实测结果：

- Input=3时user目标被转发，同时发送的QP来源目标被忽略。
- Input=1时QP来源被转发，user来源被忽略。
- Input=0期间不转发输出。
- 输入断流时未继续发布输出；切回user后未在缺少新消息时重放旧缓存。
- **Header旧了60秒的user消息仍被接受并转发。** 选择器自身不能代替上游动作时效检查。
- None或断流导致不再转发，只说明mux行为；下游驱动/控制器是否继续最后目标、如何停止，没有在此实验中验证。

早期一次实验因输出订阅者使用RELIABLE而mux提供BEST_EFFORT，未收到输出；修正订阅QoS后重跑。失败报告保留，不用于成功声明。

## 3. 新增保护层

`joint_source_guard.py` 提供带锁的进程内会话门禁：

- 单一owner、随机token；其他client不能抢占或用错误token终止持有者。
- 严格递增指令序号和命令时间；拒绝重复、倒序、未来和过期消息。
- 检查原始观察年龄、反馈年龄、关节限位、速度和单步变化。
- 心跳租约独立于动作提交，连续发送动作不会自动续租；续租也不会刷新原观察年龄。
- 输入选择改变、外部发布者被上层发现、租约过期或非法动作时锁定TRIPPED。
- 锁定后不能靠心跳恢复；只有独立停机确认后结束旧会话，新会话生成新token。

该组件不连接ROS、不发送停止请求。它仅保护合作使用该门禁的客户端，无法阻止其他程序直接向ROS话题发布；外部发布者检测也需上层持续实现。`stop_required`仅是需要停止的信号，绝不代表硬件已经停止。门禁还没有接入在用系统，不能单独解锁HardwareBackend。

最终隔离实验将门禁接在合成user源和真实mux二进制之间：有效目标正常转发，旧60秒消息在门禁处被拒绝，后续输出数为0，门禁保持TRIPPED。
