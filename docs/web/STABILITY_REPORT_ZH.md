## 本次修复

### 相机传输缺帧

原相机进程和新采集进程的 Fast DDS GUID 主机前缀分别为 `010fd8e3` 和 `010f00f6`。相机进程仍保留旧网络地址的 socket，而当前主机网络地址已变化。Fast DDS 2.14.6 源码中，同机判断比较 GUID 的前四字节；这解释了同机进程没有正常使用共享内存的现象。仅手工指定参与者 GUID 前缀不足以修复其内部主机上下文，因此没有将这种方法用于正式部署。

采集进程 UDP 接收 socket 的丢包计数在4秒内增加5。系统接收缓冲上限为212992字节，使用当前权限不能修改；本次没有修改内核网络参数。原始NV12大图订阅也受到大量丢包影响，因此没有切换正式输入来源。

确认录制关闭、机器人输入模式为0（None）后，通过已有 Apex 接口只重启相机服务。未重启机器人、遥操作、夹爪或模型服务，也没有发送运动目标。重新建立相机网络上下文后，30秒对照中，首次成功解码后的801个包全部解码成功，时间戳缺口、无输出包和UDP丢包均为0，并观测到了共享内存映射。

采集器现在每5秒记录相机/订阅者主机前缀和自身UDP丢包计数。发现网络上下文不一致时显示诊断提示；不会自动重启共享相机服务。源时间、接收时间及跨源时差门槛仍为原值。

### 训练图像处理路径

现有预览编码器将同一3840×2160 NV12拼图编码为1920×1488；录制编码器输出1920×1080。相机日志确认两条编码器输入尺寸一致。录制分支直接写MCAP，包中的 `/recorder/quad_tile/compressed_undistorted` 不等于一个始终可订阅的实时话题。

本次进行了短时、独立目录的相机录制，确认停止后读取MCAP，与同一期间的预览帧按源时间匹配。5组匹配帧的时间差约34–37毫秒；四象限排除底部变化时间戳区域后，SSIM范围0.9911–0.9942，RGB平均绝对差1.06–1.40/255。全图差异另行保留，未用裁剪后的统计宣称整幅图逐像素相同。

对于同一1920×1080 RGB输入，V1四象限拆分、缩放、补边和JPEG95/4:4:4处理，与独立训练转换器 `encode_tiles` 的四路输出逐像素一致，最大差值为0。该检查使用当前库版本，验证的是转换代码和字段布局；预览与录制的H.264编码本身不相同。

这支持当前影子推理的视野、颜色和预处理约定，不证明物理相机接线、曝光同步或任务成功率已经验收。完整图片、短录制与数值报告保存在 `artifacts/stability-20261014/image-contract/`，转换对照见 `training-preprocess.json`。

### 长时间运行的内存保留

第一轮连续测试输入有效率为100%，但约21分钟时触发了预先声明的内存增长门槛：Web与采集进程合计RSS峰值约568 MiB，相对60秒预热基线增长约151 MiB。采集进程基本稳定，增长集中在Web进程；其多个匿名线程分配区各保留了数MiB至十余MiB。第一轮被停止并保留为未通过记录，没有放宽门槛。

现在仅对 `forcevla-web.service` 设置 `MALLOC_ARENA_MAX=2`、`MALLOC_MMAP_THRESHOLD_=131072`，约束多线程大块临时数组、RPC与日志缓冲的内存保留；未修改其他服务或系统全局分配器。SQLite连接也在每次事务结束时显式关闭，读取预测摘要时不再取出整份图片BLOB。

正式复测使用与第一轮完全相同的门槛：30分钟、至少900次结果、输入有效率≥99%、RPC P95≤3秒、无错误事件、RSS峰值≤800 MiB、预热后增长≤100 MiB、文件描述符增长≤10、停止确认≤20秒。

未通过的基线完整保留在 `endurance-memory-baseline/`；修复后测试保存在 `endurance/`。图表见 `artifacts/stability-20261014/acceptance.png`，汇总文件会注明两轮门槛是否一致。

### 网页断连和服务重启

会话签名密钥改为数据目录中的权限0600文件；网页在重连时重新获取会话和CSRF信息。模拟服务强制退出再启动后，浏览器无需刷新即可重新连接，会话Cookie保持有效，旧运行标记为INTERRUPTED且不会自动恢复推理，手动新推理可用。

密钥不进入导出包。首次从旧版升级时，已经打开的旧页面仍需刷新一次。

## 已验证的故障行为

| 故障 | 操作范围 | 结果 |
|---|---|---|
| 采集暂停 | 仅暂停本项目采集进程 | 检出过期，进入WAITING_INPUT，不继续提交新预测；恢复采集后重新推理 |
| 会话持有者断连 | 关闭测试会话WebSocket | 约11秒内回到IDLE，包含10秒宽限期 |
| RPC超时 | 隔离Web实例、合成观察、真实gRPC端点 | 单次请求得到DEADLINE_EXCEEDED，进入ERROR，不自动重试；模型健康正常 |
| Web进程重启 | 仅模拟服务8097 | 自动重连、旧会话不自动恢复、手动新运行可用 |
| SQLite连接释放 | 本地临时数据库 | 事务结束后连接已关闭 |

故障报告分别为 `fault-recovery.json`、`rpc-timeout.json`、`browser-restart.json`。这些测试不发送机器人运动指令。

## 后续运行

正常启动仍使用已有用户服务，默认只采集，按网页按钮才推理。网络改变后若再次出现同机连接诊断，可先运行以下只读检查：

```bash
cd /home/user/forcevla-web
.venv/bin/python scripts/reconnect_camera.py
```

确需刷新相机连接、且已确认其他使用者可接受短暂视频中断时，可显式执行：

```bash
.venv/bin/python scripts/reconnect_camera.py --restart-camera-if-idle
```

脚本会拒绝正在录制/转换录制状态或机器人输入不是None的情况，不修改输入模式。该操作只重启相机；原网页不会自动调用它。

重新验收：

```bash
env -u PYTHONPATH -u VIRTUAL_ENV .venv/bin/python scripts/endurance.py --duration 1800 --output artifacts/new-endurance
```

原计划中的离线IK、可达性/碰撞检查、物理TCP/力觉标定与实机闭环仍属于后续阶段。30分钟软件验收不能替代这些验证。
