# 10轮后停止的调查（2026-10-15）

直接原因已确认：运行 `7ffc3305a2554a329fbef574b60d3618` 在11:30:55（北京时间）因 `browser_disconnected` 取消。前10轮共200步已完成，第11轮已取得新观察并进入规划，尚未提交该轮动作。结束时实际确认Input=None、双臂静止、夹爪释放。

进一步发现：这个错误名并不等于底层WebSocket/TCP连接已经断开。前端通过 `setInterval` 每2秒发送应用层文本 `ping`；后端仅在收到这个消息时更新会话心跳时间。执行子进程发现超过5秒未更新，就设置 `browser_disconnected`。因此，网页JavaScript不及时发送心跳，即使连接和服务器状态推送仍然正常，也会触发相同停止。

## 历史证据

- 11:25:55.383855：客户端连接建立。
- 11:27:51.604064：执行器开始本次运行。
- 11:30:51.661832：第10轮20步完成。
- 11:30:55.962263：取消及保持/释放完成，原因 `browser_disconnected`。
- 11:31:02.808680：同一客户端地址建立了新连接。
- 同一网页服务进程PID=107684从10:54:53持续运行，未在事件期间重启；系统NetworkManager日志该时段没有网络变更记录。
- 前10轮模型RPC为约1.14～1.45秒；停止原因不是模型RPC超时、达到100轮/600秒上限或已删除的夹爪到位超时。

几次连接重建间隔约306～318秒，值得进一步检查客户端或中间网络的定时行为。但连接重建记录本身不足以证明浏览器后台限频、网络断开或用户手动刷新中的哪一种。

## 无硬件的对照复现

为避免原生模拟执行器的调度截止期干扰，最终测试直接从生产 `run_planner_loop.py` 的AST提取 `cancel`、`cancellation_requested`、`read_parent` 三个原始函数，使用网页现有会话监督与真实浏览器连接。测试工作进程没有导入ROS、SDK、模型或执行器，没有设备控制接口。

待心跳正常后，只抑制浏览器的应用层 `ping`，保持WebSocket、页面渲染及服务器推送：

- WebSocket没有关闭或重连。
- 抑制期间仍收到21条服务器状态消息。
- 父进程心跳年龄0.155秒，父进程监督正常。
- 浏览器应用心跳年龄达到5.013秒时，得到 `CANCELLED / browser_disconnected`，复现生产停止标签。
- 硬件命令数为0。

另有事后65秒TCP只读采样，显示连接持续接收并确认服务器数据、客户端消息稀疏；该采样不在事故发生时，不能当作事故时刻的完整网络证据。

最早的两次辅助试验没有形成有效复现：headless页面冻结没有实际抑制定时器；使用完整模拟执行器时受到 `native_deadline` 干扰。保留这些记录，不把它们当作成功证据。

## 仍不能确定的部分

生产代码没有记录逐次浏览器心跳、页面可见性、JavaScript定时器间隔和WebSocket关闭码。因此能确定“应用心跳超时触发了停止”，也能证明“连接未断也能出现此错误”；无法追溯唯一确定当时心跳消失是页面后台/休眠、浏览器卡顿还是短暂网络异常。

建议后续将状态显示为“浏览器心跳超时”，增加上述诊断，并考虑服务端发起应用心跳、浏览器收到后立即应答，减少对浏览器周期定时器的依赖。是否调整断连停止策略属于另一项行为变更；本次调查没有修改生产停止策略，也没有重新启动真机。
