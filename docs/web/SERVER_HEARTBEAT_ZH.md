# 服务器发起的浏览器心跳（2026-10-15）

已部署到8096。刷新网页后使用新协议，不需要重新启动模型或机器人。新页面的心跳不依赖 `setInterval`；旧页面的定时心跳暂时兼容，刷新后才切换为新协议。

## 行为

- 服务端每秒产生一个带连接ID、序号和随机值的应答请求，附在现有WebSocket状态消息中。
- 浏览器收到后，先立即回复，再进行图表和页面渲染。重复状态消息不重复回复同一个序号。
- 后端校验连接归属、序号、随机值和响应年龄后更新会话心跳。重复、过期、其他连接的回复及页面可见性通知均不能续期。
- 前端兼容尚未升级的服务器时，也通过收到状态消息来发送心跳，不另设心跳定时器。
- 短暂重连沿用同一浏览器会话。已取消的动作不会因为连接恢复而自动重播。
- 真机20步模式仍在超过5秒没有有效应答时停止，原因明确记录为 `browser_heartbeat_timeout`。父进程失联及无效时间戳有独立原因。

该改动避免心跳依赖浏览器周期定时器。当页面完全冻结、浏览器退出或网络中断而无法处理消息时，仍会触发超时停止。

## 诊断

`data/connection-events.jsonl` 记录每次连接、服务器请求、有效应答、往返时间、相邻应答间隔、页面前后台/焦点变化，以及服务器和浏览器报告的连接关闭码/原因。日志按4MiB轮转，保留两个历史文件；不记录会话Cookie、CSRF令牌或应答随机值。

20步执行工作进程把停止时的心跳年龄、父进程监督年龄和连接状态保存到运行目录的 `connection_diagnostics.json`，同时写入 `status.json`。连接ID可以与上述日志对应。页面闭环面板显示往返时间和页面可见状态；历史旧错误码也会显示为心跳超时，不再直接把它解释成已确认断网。

## 验证

- 心跳与原推理API测试：19项通过。
- 原闭环和静止控制兼容测试：34项首次通过，1项原生500Hz模拟调度测试首次出现 `native_deadline`，单独重跑通过。失败记录保留，不作为本次心跳失败。
- 工作进程监督测试4项、20步循环测试10项通过。
- 真实浏览器连接纯模拟心跳工作进程：禁用全部网页周期定时器并模拟后台可见状态，14秒内持续得到14次应答，会话保持运行。
- 主动关闭WebSocket后自动重连，保留同一运行；客户端关闭码和原因正确落盘。
- 保持连接与状态推送、只抑制应答，约5.05秒后取消，记录 `browser_heartbeat_timeout`；停止后重新连接不会恢复旧运行。
- 正式8096网页只读检查：禁用网页周期定时器后9秒获得9次应答，协议为 `server_challenge_v1`，往返约2.7ms；输入有效、模型在线、无浏览器错误。
